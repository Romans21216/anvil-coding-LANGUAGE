SUMMARY
-------
Anvil is a real, early-stage domain-specific programming language for small game-like programs. It has its own syntax, parser, validation rules, diagnostics, compiler, and runtime. The current default compiler translates supported programs to C/MSVC; an experimental native option emits AMD64 and PE32+ directly for numeric programs and an initial rectangle/circle/line 2D runtime. The requested no-C/no-Rust engine remains incomplete.

The fairest description is a small game scripting language connected to a Windows software-rendering prototype. Its syntax is approachable and it has a working path from source to executable, including parameterized functions and numeric loops, but it is much closer to a learning project than to a complete game engine or mature language ecosystem.

WHAT ANVIL IS GOOD AT
---------------------
1. Readable source: named functions use a small BASIC/Lua-inspired set of commands, expressions, branches, and explicit end markers.
2. Native compilation: the direct backend emits Windows x64 machine code and PE executables for numeric programs and an initial 2D rectangle/circle/line runtime. Broader engine programs currently use the existing generated-C/MSVC path.
3. Small interactive scenes: the runtime provides 2D drawing, basic 3D primitives, a perspective camera, keyboard controls, a fixed-step update loop, and a way to combine a 2D HUD with 3D content.
4. Reusable numeric functions and loops: functions support parameters, numeric return values, recursion, and function-local numeric state. Inclusive `for` ranges support ascending or descending steps; `while` loops support condition-controlled repetition.
5. Procedural math: seeded random values, deterministic gradient/fractal noise, and common math operations are available.
6. BVH ray tracing: `ray_sphere(x,y,z,radius)` is a built-in drawing function using CPU BVH traversal, diffuse lighting, specular highlights, and hard-shadow queries. The current documented limit is 32 ray-traced spheres per batch.
7. Early developer tools: TOML project manifests, examples, tests, a VS Code syntax extension, and separate language, engine, compiler, and multiplayer guides are provided.

WHAT ANVIL IS NOT GOOD AT YET
-----------------------------
1. It is not a complete engine: physics supports up to 128 fixed-step 2D circle and axis-aligned box bodies, configurable active capacity, restitution, and Coulomb friction. There is no continuous collision detection, polygon or 3D bodies, or joints. A general asset pipeline, broad texture formats, sprite animation, texture atlases, 3D mesh textures, audio engine, animation framework, scene graph, complete editor, and broad GUI system are also absent; the C-backed runtime includes bounded BMP-based screen-space sprites.
2. Rendering is limited: conventional drawing uses a fixed-size software renderer rather than a modern GPU renderer. The C-backed window can be resized with aspect-preserving letterboxing, while its internal resolution remains 960×600. The direct backend resizes its 2D rendering surface to client dimensions. The earlier independently verified C-backed implementation includes near-plane clipping for triangle faces, grid segments, and rasterized spheres. Far-plane and side-frustum clipping, mesh import, texture mapping, and performance profiling remain future work.
3. Only one ray-tracing path is implemented: CPU BVH is available. The runtime exposes `ray_backend(name)` and `ray_backend_available(name)`. The selector successfully chooses BVH; hardware-accelerated RTX/DXR and Embree are not implemented and cannot be selected successfully.
4. The language remains narrow: fixed-size global and function-local numeric arrays are now implemented, but dynamic arrays, user-defined types, namespaced modules, static types, and a general string model are not. Function parameters, return values, recursion, function-local numeric state, numeric `while`/`for` loops, and array bounds checks are implemented.
5. Multiplayer is experimental: the UDP API exchanges a numeric value with one peer. It lacks reliable delivery, authentication, encryption, matchmaking, replication, and robust peer lifecycle handling; it is only appropriate for trusted LAN experiments.
6. The build target is narrow: broader engine builds currently use Windows/MSVC with generated C; the direct AMD64/PE backend compiles numeric programs, checked global arrays, and an initial 2D window/rectangle/circle/line runtime without generating C/Rust or invoking another compiler. Native engine parity is incomplete, and a cross-platform runtime is not implemented.
7. Efficiency claims are unproven: there is no benchmark suite comparing compile time or runtime performance. The software renderer and ray tracer are CPU-bound, so “hyper-efficient” is not supported by measurements.

HOW CLOSE IS IT TO A REAL PROGRAMMING LANGUAGE?
------------------------------------------------
In the technical sense, Anvil is a programming language: it defines syntax and semantics, parses and validates programs, reports errors, translates code, and executes through a runtime. It is not merely pseudocode. It is a small compiled domain-specific language.

In maturity, it is still an early prototype. The core can support simple, reusable programs, including numeric `while` and `for` loops, but it lacks collections, user-defined types, namespaced modules, a mature standard library, portability, a debugger, and mature diagnostics. The game engine is less complete than the language implementation.

Overall, Anvil is close to a custom scripting language for simple demos. It is not close to a general-purpose ecosystem or production game engine. The idea is credible; substantial work remains in language breadth, runtime systems, tooling, portability, and long-term compatibility.

MATURITY SNAPSHOT
-----------------
Language syntax, validation, and C generation: Working prototype
Functions with parameters, returns, recursion, and locals: Implemented for numeric values
Numeric `while` and inclusive `for` loops: Implemented and covered by native executable tests
Fixed-size global numeric arrays: Implemented with zero initialization and checked indexing
Fixed-size function-local numeric arrays: Independently verified in both backends with zero-initialized per-call heap storage, cleanup on return, and checked indexing; 8,192-element per-function and 16 MiB active-call limits; native sample prints 27
Native Windows executable generation: Existing C/MSVC path plus experimental direct-x64 numeric and initial 2D subset; full native runtime parity is incomplete
Basic 2D/3D rendering and camera controls: C backend provides these with limits; direct backend currently renders opaque 2D rectangles, circles and clipped lines
BVH CPU ray-traced spheres: Implemented, limited to 32 per batch
Ray backend selection and availability built-ins: Implemented and verified; only BVH is available; DXR/Embree unavailable
BMP-based 2D image resources and sprites: C-backed prototype implemented and exercised; native port remains absent
Fixed-step 2D circle/axis-aligned box physics: Implemented as a bounded prototype with active capacity 1–128, restitution, and Coulomb friction (no rotation, CCD, joints, or 3D/polygon bodies)
RTX/DXR and Embree: Not implemented
LAN multiplayer: Minimal UDP prototype
Internet multiplayer: Not implemented
Final compiler target: Direct machine code; no C/Rust shim required by native path
Cross-platform runtime: Not implemented
Performance evidence: Not available
